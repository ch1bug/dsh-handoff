# 0001 — handoff 能力独立成仓：能力归能力仓，策略归项目

Status: accepted（2026-11-24，grill 拍板后建仓；实现待第一跳）

## Context

`dsh-matt-preset` 里 handoff 分三层：判据（`workflow-enforcer` 的批次收尾提醒）、内容
（`handoff-tool` 硬编码的文档节）、执行（起会话 + 无人值守唤醒编排）。用户要求
**只把 handoff 本身做成能力**、独立建仓维护，**怎么用跟着项目走**。

## Decision

1. **本仓只提供能力**：
   - 核心库（深模块、纯函数、无 IO）：事实 + 模板**文本** → 交接文档；
   - 薄 tool 适配器：`path` / `text` 二选一，读文件与缺件/坏件的**响亮失败**在适配器；
   - 执行面：fresh / fork、侧边栏挂载、首 turn、首 prompt。
2. **不提供策略**：不读状态源、不判「该不该交接」、不内置项目模板；状态源与模板是
   消费方项目的配置与规则。
3. **消费方式**：消费方以**精确锁版本**依赖本包；第一个消费者 = `dsh-matt-preset`，
   preset 行以 package specifier 挂载 tool 行。
4. **两跳迁移**：第一跳只搬库（消费方 tool 退化为薄壳）；第二跳搬 tool 行。
5. **失败面**：模板缺件 / 坏编码 / 形状不符 → 响亮失败（不静默降级为内置默认）。

## Consequences

- 本仓需要自备守卫套件、发布流程（prepublish 校验）、与 DSH 运行时的版本矩阵；
  运行时锚纪律从消费方仓的既有做法派生（不另造第二套比较器）。
- 消费方行为依赖本包可用性 → 精确锁版本 + 发布校验 + 未装/版本不符时响亮失败。
- 中间态存在「壳 + 库」双版本面，须在第二跳收敛。

## Non-goals

- 不是工作流引擎、不是批次管理器、不提供状态源适配器（无第二个真实状态源前不开缝）。
- 不读消费方的项目文件位置（模板位置由消费方传入）。
- 不把模板/策略写进系统提示词（缓存纪律，消费方 #200 实测）。
